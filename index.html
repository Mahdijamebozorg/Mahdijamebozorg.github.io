Featured AI Platform Work

CI/CD for All Product Repositories

One Azure DevOps YAML pipeline per repository for the .NET backend, the Next.js web app (IIS/iisnode), the Flutter PWA and a Thrift service. The branch decides the environment: dev, test or production.

  • Shared build, deploy and review logic lives in one central templates repository; product repositories keep only a short entry file, so a change is made once and reaches every pipeline.
  • Each run is one stage: detect changes (CI-only changes skip the build), build, deploy, AI review. When a dev run finishes, the dev environment is already updated.
  • Two deployment paths: IIS on the internal server for dev; packaged transfer over SSH (tar.gz + scp) to external hosting for test and production, with automatic rollback for backend and mobile web production deployments.
  • Secrets live only in variable groups and secret pipeline variables, never in YAML. Pipeline completion triggers the knowledge pipeline.

Shared Knowledge Platform for Coding Agents

A FastMCP server that the Claude Code and Codex agents of all three teams connect to. Users sign in with their Azure DevOps personal access tokens, every call is audited, and tools can be restricted to chosen users without a restart.

  • Serves code graphs of the three repositories, the 594-endpoint backend API contract generated from Swagger and split into searchable sections, documentation, and read-only Grafana logs and metrics (Loki/Prometheus).
  • Exact backend facts from a custom Roslyn (C# compiler) exporter: endpoints, authorization policies, where each error code is produced, callers, interface implementations and the permission catalogue with where each permission is checked.
  • A separate pipeline rebuilds and publishes all generated knowledge after every dev build and nightly, deciding per repository what to rebuild, with skip switches per step.
  • A Git/Markdown knowledge base organised with Diátaxis (also an Obsidian vault). ADRs act as machine-readable team contracts: agents query the decisions that apply to the files or endpoint they change, must not contradict them silently, and report missing information as a “knowledge gap”.

AI Code Review & Release Reporting in CI/CD

Every pipeline run ends with an AI step that sends the diff to one central review service. Each audience gets its own report: a full technical review for developers on dev, a review for the test branch, a product-level report for managers (sent only when there is something to report) and a release report for production.

  • Reviews check the change against the API contract, the team decisions and the linked task. A behaviour change without a matching Swagger update counts as a critical finding.
  • Critical findings are tracked until a later review confirms them fixed; coding agents see the open findings on a file before they edit it.
  • Reports are delivered to Bale, Telegram and Slack and kept as pipeline artifacts.
  • Prompts live only in the central service; pipelines name a prompt and never copy it. If the service fails, the pipeline posts “no report” and does not fail.

Central AI Agent & Ops Bot

One assistant on the Bale messenger that routes requests to skills. Access per user is defined in a policy file (skills, boards, quota and model); users can be served by the Claude CLI or by the LLM gateway, with the model chosen by name.

  • Task analysis before development: classifies a task as ready, needs clarification, needs decision, needs investigation, blocked, needs split or close; cross-checks it against the API contract and the code, groups open questions by who must answer them, and keeps a history of analyses.
  • Drafts ADRs and opens them as pull requests through a least-privilege bot account that can only create branches and pull requests; humans review and merge.
  • A weekly management report (task health, sprint flow, stuck work, incoming requests, analyses) and platform monitoring.
  • The administrator manages users in natural language; the bot only proposes a change and applies it after explicit confirmation, with a re-check, a backup and a change log.

How I build

  • Read-only by default: every write path is a narrow, documented exception that needs a human confirmation step.
  • Least privilege and per-consumer tokens; secrets are never stored in the repository.
  • Personal data never leaves company servers unmasked.
  • One source for shared logic: CI templates and review prompts live in one place.
  • Generated knowledge lives on the server, not in Git.
  • Configuration-driven, self-contained modules: the platform is designed to become one reusable product.
